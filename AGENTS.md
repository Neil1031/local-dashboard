## 2026-10-08 owner-scoped execution policy

This owner instruction supersedes conflicting older approval/Gate wording for the same approved work. Before applying it, verify live GitHub metadata and actual target identity: repository owner must be `Neil1031`, the target must belong to that personal project, and no company system or data may be affected. Inspect fork parent/source provenance. Exclude every company project/repository/database/server/deployment, company local copy, company-derived fork unless explicitly owner-authorized, and non-`Neil1031` repository. A folder name or shared working directory is not proof; if identity or authority cannot be established, do not apply this policy. Company work retains its separate workflow and authorization.

- Follow **BACKUP → VERIFY → MODIFY → ACTIVATE → READBACK**. Before changing the affected program/data/rules, preserve a restorable backup and verify its identity/completeness and restore route. Freeze the intended delta, preserve unrelated dirty changes, and run the necessary checks. After successful review/checks, complete the required normal Git integration/push, deployment/activation and actual readback within the same approved goal; do not ask again solely because the action is merge, deployment, or a DB write, or because validation used SOURCE/TEMP first.
- Use safe transactions for approved DB changes; check the result and roll back or restore the verified backup on failure. Account for active writers and DB sidecars/consistency when relevant. This workflow policy does not change Dashboard's read-only external-source contracts, grant a new feature/data scope, or permit bulk activation of unrelated products/PRs.
- Keep proportionate tests, independent review, evidence/provenance, process identity checks, and transaction/restore protection. Reuse these existing Works and evidence; remove redundant approval loops and unnecessary repeated Stage Gates. Sol investigates, repairs, verifies and continues within scope. Escalate only a real scope/product decision, unavailable credentials/authority, an actual policy rejection or another substantive blocker; never bypass a policy rejection using another tool or shell.
- Historical `STAGE-*`, deployment acceptance snapshots and old pending-Gate/status text remain evidence of their original work, not current instructions to repeat acceptance or wait for another approval. Apply this policy to active operations without rewriting historical evidence or changing product semantics. Owner defines new goals and scope; an old task is not restarted by this governance synchronization.

GPT retains direction and one Final at actual Stage completion. Preserve §0 company exclusion, Owner Doc limits, honest test status and source/PIT/rights/HOLD/spent/STOP boundaries. A cancelled automatic-deployment feature is not restored by this workflow; do not bypass Claude limits by account/model switching.
- At Stage completion, Sol/Reviewer briefly record work, actual start/finish/elapsed and test/review outcome in the normal PR/handoff; Orchestrator summarizes role times, whole-Stage wall-clock and completion/deployment status. Separate recorded waits, do not sum overlapping work as elapsed, and mark missing values UNKNOWN. No separate timing/evidence system or notification-only proof.
- [Owner Doc Lightweight Sync Policy](docs/PERSONAL-PROJECT-GOVERNANCE.md#74-owner-doc-lightweight-sync-policy) is authoritative: Sol submits `DOC_CHANGE_REQUEST` and never edits Owner Google Docs; Management directly edits only evidence-backed status markers / very short operational identities, and uses comments for content changes. Comments are verified available; do not repeat capability tests. Actual comment failure returns `OWNER_DOC_CONTENT_SYNC_PENDING` / `OWNER_DOC_MANAGER_EDIT_REQUIRED`; full body sync requires separate `OWNER_DOC_BATCH_SYNC` authorization.
- All Dashboard-owned UI wording uses `ui/i18n.mjs` and the shared flat `ui/locale-zh-TW.mjs` / `ui/locale-en.mjs` resources. Every new key includes both locales and identical placeholders in the same change.
- `zh-TW` is the default. The browser preference uses `local-dashboard.locale.v1`; no server/config/DB locale setting.
- Preserve source-authored text, user display names, canonical design text, IDs, timestamps and provenance. Unknown source codes stay raw; known code translations retain the raw code.
- Locale changes update held presentation text only. Never call navigation/show/load/refresh or source/API requests on a locale change. Preserve filters, paging, focus and open dialogs.
- Translate with textContent and allowlisted text attributes; never interpolate translation HTML.
- For any UI change run localization coverage/parity tests and the relevant browser regressions. Keep parser, identity, race, privacy and source assertions intact.
