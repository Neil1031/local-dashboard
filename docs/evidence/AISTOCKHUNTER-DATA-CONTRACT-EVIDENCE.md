## Daily scan evidence

**Current daily accumulation path:** `daily_accumulation.py:217–235` calls `scan_unexplained_volume(... observation_only=True, signal_source='DAILY_ACCUMULATION')`. Its outer run ID is a canonical UUID hex; `accumulation_result` is keyed by that ID **and target date** (`daily_accumulation.py:292–316,367–376`). The scan result contains `scan_date`, method `robust-log-volume-v1`, universe basis, `scanned_symbols`, `candidate_count`, `total_candidates_before_limit`, `truncated`, `classification_counts`, `skipped_counts`, config, candidates and a watchlist warning (`unexplained_volume.py:211–226`). The outer daily result carries source statuses, market validation, `classification_status` and overall status. These are separate levels of state.

**Older standalone daily job:** `unexplained_volume_daily.py:768–841` claims integer `unexplained_volume_run.id` for `requested_date`, records a nullable `scan_date` and finish time, and stores scanned/candidate/strict-unexplained counts, provider status, outcome summary and output paths. Its lifecycle is not interchangeable with the UUID accumulation run. A failed run's default zero counters are not a valid zero-candidate finding.

Candidates are selected after baseline/volume/anomaly gates, then ordered by descending score, ratio and symbol; rank starts at 1 (`unexplained_volume.py:124–166`). Classifications are `UNEXPLAINED_VOLUME`, `POSSIBLY_UNEXPLAINED`, `PUBLIC_INFO_COVERAGE_GAP`, `PUBLIC_INFO_FOUND`, `POST_CLOSE_PUBLIC_INFO_FOUND`, `MECHANICAL_EVENT_EXCLUDED` (`unexplained_volume.py:19–24,482–497`). Incomplete cause checks can downgrade coverage to `PARTIAL`; `analysis_eligible` is set by existence of a dated `google-news-rss` coverage record, **not** by proof of complete coverage (`unexplained_volume.py:169–185,448–457`). UI must show classification, basis, coverage, flags and evidence together.

Persisted signal fields include anomaly score/rank, volume ratio/z-score/baseline, same-day return inputs, related/official/relevant public-info counts, `coverage_status`, evidence and risk flags (`db.py:420–455`; `unexplained_volume.py:430–555`). `active` rows are first invalidated for a re-scan, surviving candidates are upserted as active, and history records both state changes (`unexplained_volume.py:187–208,757–817`). `finalized_at` remains nullable when coverage/classification has not met its rule. The current signal row's UNIQUE `(symbol,signal_date)` and absent `run_id` mean a Dashboard export must **explicitly bind a signal to its source run/observation**; a consumer must not manufacture that relationship from the current row.

**Zero and null rule:** `db.py:439–440` declares `return_1d` and `return_5d` `NOT NULL DEFAULT 0`; this is a storage default and the calculation path supplies values separately. **`0 DEFAULT != observed 0`**. These are not the nullable future-horizon `forward_return_{1,3,5,10,20}d` fields. The current observation-only path suppresses all forward outcomes to `None` (`anomaly_modes.py:117–120`; `unexplained_volume.py:524–526`); research mode computes a future return only with sufficient `AVAILABLE` sessions and valid price basis (`unexplained_volume.py:724–750`). A nullable forward return must stay unavailable/pending, never be rendered as 0%.

## Accumulation evidence

`accumulation_scope` fixes the start date; ordinary daily runs check it and cannot imply pre-scope collection (`daily_accumulation.py:292–307`). Targets are bounded: current due day first and at most two recent unresolved/delayed days within seven calendar days (`daily_accumulation.py:270–289`). Each target has its own saved result, source attempts and actual `finished_at`. Source successes survive other source failures, but do not waive completeness (`daily_accumulation.py:1–5,359–377`). Overall report state is `FAILED` if any target failed, `SUCCESS` if all are `SUCCESS` or saved non-trading days, otherwise `PARTIAL`; deferred dates, unresolved revalidation or unverified owner can downgrade a would-be success to `PARTIAL` (`daily_accumulation.py:378–384`). `NO_TARGET_DUE` is collection state, not proof that all old data is complete.

`classification_status='WARMING_UP'` means all scanned symbols were skipped for insufficient baseline history; it is distinct from overall `SUCCESS`/`PARTIAL` (`daily_accumulation.py:217–236`). Other observation status includes `OBSERVATIONS_AVAILABLE` or `NO_MARKET_DATA`. Read-only `inspect_accumulation` validates latest saved target, source timing, market coverage, journal completion and pending revalidation (`daily_accumulation.py:423–505`); malformed persisted source JSON produces `PERSISTED_SOURCE_INVALID` rather than invented success (modified worktree lines 395–420). The weekly problem `UNRESOLVED_REVALIDATION` comes from the journal; it is not a per-signal classification.

## Weekly evidence

`weekly_accumulation_check.py:15–24` selects the latest **due** Friday at 22:00 Asia/Taipei and inspects that Monday–Friday window, clipped by scope start. `inspect_week` reads original DB/journal with `mode=ro`, checks integrity, calendar/open markets, each eligible day and outstanding journal runs/revalidation; it does not fetch, migrate, repair or run a strategy (`weekly_accumulation_check.py:25–99`). Day states other than `SUCCESS` or evidenced `SKIPPED_NON_TRADING_DAY` produce `DAY_INCOMPLETE:<date>`. Unfinished operations and unresolved claims produce `UNFINISHED_RUN:<id>` and `UNRESOLVED_REVALIDATION`. Overall status is `SUCCESS`, `FAILED` or `NOT_DUE` for a pre-scope week (unless an integrity problem makes it fail).

`run_weekly_check` writes `weekly-checks/<week-end>-<check-run-id>.json` and overwrites `weekly-checks/latest.json` with the same result (`weekly_accumulation_check.py:101–107`). `latest.json` is a **pointer-like latest copy**, not an immutable week snapshot and **not a completeness guarantee**. It can contain `FAILED`/`NOT_DUE`, and the check itself reflects observations readable at check time rather than an atomic source-week snapshot (`README.md:126–128`). Consumers need `week_end`, `check_run_id`, `checked_at`, `status`, problems and revalidation state, not just filename existence.

## Candidate semantics

`candidate_signal` is written by the separate legacy strategy scanner (`scanner.py:297–325`). The current daily entry calls observation-only `scan_unexplained_volume` and sets `strategy_status='OUT_OF_SCOPE'` (`daily_accumulation.py:217–225,264,311–314`); it does not call that scanner. Its `candidates` are anomaly **watchlist observations**, accompanied by a warning that they are not evidence of insider trading (`unexplained_volume.py:211–226`). Consequently, Dashboard must not use `candidate_signal` as today's daily accumulation feed or treat `analysis_eligible` as trading authority. The future export should issue an explicit candidate/watchlist type and decision authority `NONE`.

## Recommended Dashboard boundary and corrections

The source provides real, useful fields, but these are private schema/artifacts with distinct run identities and mutable latest copies. Source inspection and a bounded search of `stock_hunter/`, `tools/`, `README.md` and `docs/` found no declared `contract_version` or normalized Dashboard-facing export; this is an inspection result, not a claim about undiscovered external interfaces. The Design Space recommendation remains supported: a **future source-owned, read-only `ai-stock-hunter-export-v1` normalized JSON**. It should identify accumulation run/target, scan observation/history version and effective date separately; preserve source `PARTIAL`/`WARMING_UP`/`FAILED`/unknown/revalidation states; state candidate authority `NONE`; distinguish measured zero from default zero and pending future outcomes; carry source-code/contract version and coverage. Dashboard would consume it through an adapter without opening or writing the source DB.

The initial Data Contracts inventory needed corrections: it grouped `unexplained_volume_run` with current accumulation, did not state that observation-only forward outcomes are suppressed, and did not explain the absence of a signal-to-run FK or the separate legacy Markdown exports. Those are corrected in `DASHBOARD-DATA-CONTRACTS.md`. The product sitemap and prototype require no change.
